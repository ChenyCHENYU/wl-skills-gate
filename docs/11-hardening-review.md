## 兼容与管理边界

0.4 的 promote --push / allow-any 禁用，旧 unsigned 证明不能部署，旧修复计划需重新预览，基线补风险/发生数，工具 exit=1 需显式契约。迁移先样板再推广，固定包/规则/模板版本。

修复扫描通过只进入待复验；主台账完成独立复核、必要的环境验证后关闭。包不声明自动建单/发送消息已实现，不把群送达当认领，不把本地测试当生产验收。


## 复核结论与样板准入

共享 Gate 包的方向正确：统一执行/裁决/证据契约仍保留在一个版本化包，未来按权限把命令接入不同作业，无需先拆成多个 npm 包。检查/候选、Review、证明签发、共享分支更新、部署、台账通知分别配置执行入口和权限；共享引擎不能替代平台保护和管理责任。

0.5.0 的结论是“上述反例和分发检查通过，可进入样板接线”。下一步按以下顺序验收：

1. 前后端各选一个真实样板，先以只读 standard 接入实际类型/编译/规则/测试与结构扫描，抽核检查范围、版本、必测用例和每条问题定位。基线经批准后锁定，质量底线不得例外。
2. 采用无特权候选作业、独立非作者 Review、权威来源查询后的签发、bare 更新控制器；真实账号演练普通 push 被拒、删 CI 不能绕过、并发候选失效和失败证据归档。部署使用单仓签名清单，再补平台的双仓发布组合核验。
3. D1～D4 与样板同步接线：指纹幂等入主台账，实名主备与复核人，飞书/企业微信群消息提供认证的问题/报告/流水线跳转，认领与复验写回台账，无人认领或逾期自动升级。检测漏跑/权限漂移和通知失败也须有对账兜底。
4. 以一个真实问题完成“发现→阻断→建单→推送→认领→修复→独立复验→关闭”，保存各环节证据后再扩项目。消息发送成功、扫描转绿和本地包测试分别记录，不能据其中一个宣布问题已闭环。

本轮未发布 registry、更新真实共享分支、修改平台权限、部署或发送群消息。以上平台项保留为明确待接入工作，避免把包的代码能力误记为组织管控已生效。
