## 1. 本轮发现与已修复问题

| 边界 | 之前的风险 | 0.5.1 行为与证据 |
|---|---|---|
| ESLint 全量目标 | ESLint 8 无文件参数可能返回空数组和 0，漏扫仍显绿 | 默认传 `.`，支持 targets/args；空扫、全忽略、增量漏文件 invalid；记录实际 coverage |
| 范围和路径 | command 覆盖破坏候选增量；Git 文件名带中文/空格；临时目录物理路径别名 | 推荐 bin+targets/args；Git -z 精确文件名；物理路径归一后拒绝项目外结果；command 仍禁止配增量 |
| release 证据 | 增量绿色报告可用于发布 | run 参数和证明语义都拒绝 release 的 staged/base/head；发布必须全量 |
| 源码摘要 | 跟踪的 dist/target 等也被排除；自定义报告目录可隐藏/覆盖源码 | 所有 tracked 内容参与摘要与脏状态；报告排除仅适用未跟踪生成内容；输出不覆盖根/跟踪源码、不经项目内符号链接 |
| 原始诊断 | 原生执行失败被“没有实际版本”遮蔽 | 保留原始执行原因，版本核验未完成如实记录 false |
| 基线与例外 | 候选未传批准摘要；检查绿后签发才失败 | 受控检查提前核对，存在空文件也需批准；promote 传递两个批准摘要 |
| 准备失败 | 候选只剩“依赖准备失败”，上下文丢失 | preparation 引用脱敏 dependency-prepare.json，保留退出码、时间、输出、超时和截断 |
| 目标并发 | 最后读 HEAD 后发生并发，普通 push 仍可能快进成功 | 验证候选父提交后，以明确批准旧 SHA 的 lease 更新；push 瞬间祖先并发实测拒绝 |
| 修复恢复 | 链接替换或 HEAD 改动；恢复后仍保留尝试绿色/已修复列表 | 不安全变化失败关闭；安全恢复后再次扫描、核验摘要、fixed 清空；HEAD/快照异常或恢复不完整转人工 |

ESLint 参数依项目配置确认，尤其 eslintrc 的扩展名与 flat config 文件匹配不同。[ESLint 8 官方 CLI](https://eslint.org/docs/v8.x/use/command-line-interface)。Git 显式 lease 只有远端目标等于指定 expect 才更新；本包还验证候选的第一父提交就是批准目标，限制为该目标的快进。[Git push 官方说明](https://git-scm.com/docs/git-push)。

## 2. 代码能力还不能替代哪些监督

1. **有扫描证据，不等于覆盖完整。** ESLint 非零扫描数不能证明所有 Vue/TS 文件都纳入；JUnit 有用例不能证明必测业务场景已覆盖；ArchUnit 有结果不能证明目标模块都匹配。登记预期根目录/扩展名/模块/场景、批准排除项、实际覆盖与缺口。规则版本变化后重新校准基线，不能拿数量下降当改进。
2. **有签名，不等于当前授权仍有效。** 平台权威查询真实 job/Runner/模板/身份、批准摘要与撤销状态；缓存有期限。当前包执行离线内容、签名与时效核验，不提供内网来源查询/在线撤销服务。
3. **有失败事件，不等于没有漏跑。** 建 expected_run，按请求、候选、共享 HEAD、发布和必需检查对账；Runner 崩溃/整条取消也可能没有 always 上报。失联与缺数据独立触发 A21/A22/A27。
4. **有机器人消息，不等于有人接单。** 飞书/企业微信由独立通知作业持凭据，平台响应成功只算投递接受。认领、延期、复验、关闭由主台账授权和审计。普通微信群只有经批准并实测的接入才登记可用，不能假定通用 webhook 能力。
5. **扫描消失，不等于业务恢复。** pending-verification 绑定修复 SHA、原失败场景、影响范围、复核人；现场缺陷还核对目标环境生效。恢复止损与根因整改分开。
6. **本地文件白名单，不等于操作系统沙箱。** fixer、依赖安装和检查都可能执行作者代码；隔离 worktree/Runner、凭据与缓存的责任在平台。特殊文件/submodule 暂不支持完整来源绑定时拒绝。
7. **目标 CAS，不等于多引用原子事务。** 当前 push 条件保护目标；源分支最后查询到更新之间仍可变化。严格要求最新源时，增加服务端校验/固定源引用/平台锁；不同环境的实际分支保护仍须演练。

## 3. 项目与流水线如何分工

| 位置 | 放什么 | 准入与归档 |
|---|---|---|
| 项目 quality/ | 受审批 policy、rules.lock、基线/豁免；适用与覆盖配置引用；只读扫描薄适配 | 锁 Gate/检查器版本；.vue/.ts、Java 模块与必测场景真实覆盖 |
| 本地/个人分支检查 | fast 暂存反馈、standard 全量；修复在隔离工作区 | 不持有特权凭据；退出 0/1/2 如实保留；不能充当部署证明 |
| 无特权候选作业 | promote：准备依赖、实际范围检查、bundle、promotion-record、诊断日志 | 传平台批准 policy/rules/baseline/waivers；不更新共享分支 |
| 独立 Review/签发 | 身份与来源查询、候选 Review、attest | 非作者 Review；候选/作业/摘要绑定；私钥隔离；不盲签上传报告 |
| 受控更新作业 | promote-apply：核对证明与 Review、源/目标、bundle/父提交、条件更新 | 固定 remote、同目标串行化、分支保护；审计前置并核实最终 HEAD |
| 构建/发布作业 | release 全量、manifest、签发、verify-artifact、双仓组合 | 实际制品/配置/数据脚本、环境、SHA 匹配；冒烟和观察记录 |
| 治理作业/既有服务 | inbox/主台账/责任路由/outbox/认领复验/定时升级与对账 | 一个权威状态；durable 存储；认证跳转；通知失败独立兜底 |

共享包继续集中维护。无需将 lib/run.js、gate.js、promote.js 复制进每个仓库；流水线拆成不同权限的作业，各自调用固定版本包。GitLab/Jenkins 模板引用中央版本，业务仓库引用 policy；特权动作保持平台控制。

前端建议配置如下，扩展名参数按真实 ESLint 模式补齐，勿照抄成覆盖验收：

```yaml
- id: FE-ESLINT
  tool: eslint
  bin: node_modules/.bin/eslint
  targets: [src]
  versionCommand: node_modules/.bin/eslint --version
  profiles: [fast, standard, release]
```

存在基线/豁免时，各受控阶段都传 `--expect-baseline-hash` 和 `--expect-waivers-hash`。即使文件为空也不视作 absent；平台统一下发批准值。改 targets/args/排除项须重新审批 policyHash，不能仅更新示例后沿用旧批准。

## 4. 管理环节本轮细化

具体契约见落地执行附录 C，重点是：

- 问题聚合键与每次运行的 eventId 分开；复发使用 generation，转换使用 stateVersion 条件写入。按权威运行顺序处理，不能按网络到达或 SHA 字典顺序决定新旧。
- issue 状态与通知意图同事务；外部主台账采用持久写入意图、幂等、确认与对账，不能假定跨系统事务。重试、租约、失败队列和独立心跳首期就有最小实现。
- 漏跑巡检首期覆盖样板必需检查；没有采集数据的规则标待接入。表中必须区分“已实现、已接线、已验收”，不将 27 条预警都标正常。
- 绿色复验绑定当前问题代次、修复 SHA、规则/批准、必测场景、环境与有效期；旧卡片/旧绿报告不能关闭新失败。
- 修复发布准入避免死锁：证据完整且批准范围内的修复版本可进入目标环境复验；其他新增风险不随修复单放行。
- 旧制品 proof 可能过期。普通验证默认 1440 分钟，恢复须取得新受控证据或专用紧急授权链；当前包没有专用恢复授权命令，禁止篡改时间。
- 管理者看漏跑、未认领、逾期、复发、复验积压和平台失联；开发看具体证据与修复入口，不以告警数量考核个人。

## 5. 验证证据与实际边界

包级 `npm test`：**93 单元 + 29 fixture + 17 本地集成全部通过，0 跳过**。新增 20 单元和 4 集成针对上述执行/恢复/并发边界；Git 竞争使用本地 bare remote，临时测试密钥仅在临时目录。

隔离闭环再次使用取自 wl-ui-produce / wl-produce 的代表代码和真实 ESLint 8、TypeScript、Java/JUnit。真实扫描、修复、候选、签名、制品核验与本地恢复可以执行；平台审批身份、台账/群投递、双仓发布流程仍是显式模拟。验证产物在工作区 output/wl-gate-deep-review/2026-10-09，详细计数以该目录的 verification-summary.json 为准；旧演练目录保持原样。

上轮真实项目全量仍存在前端类型/关键跳过用例、后端私有 parent POM/质量接线前置等阻断。本轮修复共享包不会自动解决业务错误，不把局部探针绿写成整仓绿，也不替业务项目改配置、基线、代码或安装依赖。

上轮沿用的管理模型还有明确简化：ingest 没有代次复发与乱序裁决、close 没有完整批准/范围/时效绑定、releaseAllowed 是“全项目未关闭即拒绝”的粗规则，通知状态是本地模拟接受。它们没有作为生产实现交付，也没有因本轮 88 场景通过就被标为已完成；附录 C.2/C.5/C.6 的真实验收必须覆盖这些缺口。

## 6. 接线前的具体验收顺序

1. 工程治理 A、前后端检查器 R、平台 R 确认适用/覆盖与批准版本；修复前后端实际检查前置，得到完整 effective POM、Vue/TS 文件覆盖和必测清单。
2. 在样板隔离分支跑只读门禁、归档及两个受控候选，验证失败与 invalid 都阻断；使用真实普通/受控账号演练保护分支、最终 CAS 和模板防绕过。
3. 平台来源查询及签发隔离验收后，接实际 Jenkins 制品/环境/双仓组合/冒烟；验证过期旧版本恢复方案与修复发布准入。
4. 同期完成 D1～D4/D6 和样板范围 D5：真实台账一单、实名主备、测试群认证跳转、认领/期限/复验/关闭、漏跑/通知故障兜底。
5. 附录 C 的重复、乱序、复发、漏跑、过期、宕机恢复、权限与告警失联用例实际通过后，标样板“已闭环”；再按覆盖分母推广。

本轮没有发布包、push 真实远端、部署服务或发送真实群消息。
